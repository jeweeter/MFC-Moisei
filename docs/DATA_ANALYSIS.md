## 2. Качество HTML в текстовых полях

Поля заполнялись через визуальный редактор копированием из MS Word. В результате в них лежит не текст, а разметка Word:

* инлайн-стили на каждом `<span>`/`<p>` — до 90% объёма поля;
* служебные namespace-теги Word: `<o:p>`, `<w:WordDocument>`, `<m:oMath>`, `<xml>`;
* условные комментарии `<!--[if gte mso 9]>` с CSS внутри;
* **7** изображений, вшитых в текст как base64 (одно поле услуги «Подтверждение личности для приложения "Госключ"» весит 862 КБ, из которых полезного текста — 146 символов);
* html-сущности `&nbsp;`, `&quot;`, местами экранированные дважды.

**Следствие.** Наивный `strip_tags` даёт нечитаемое месиво, а поиск по сырому полю ищет по слову `border-box`, а не по тексту регламента. В проекте это решено конвейером `backend/app/ingest/html_clean.py`, который восстанавливает структуру (абзацы, списки, нумерацию, таблицы, ссылки) и убирает 53.7% объёма.

**Предложение 1 (изменение).** Хранить в базе знаний размеченный текст в структурированном виде (Markdown или ограниченный набор тегов `p/ul/ol/li/b/a`) и запретить вставку из Word без очистки. Это снимает необходимость в очистке на каждой стороне-потребителе и убирает риск потери смысла при разборе.

## 5. Административные регламенты — главный пробел

ТЗ прямо указывает: «Важным моментом является наличие по каждой услуге административного регламента… утверждённого каким-либо нормативным документом». В выгрузке отдельного поля под НПА нет вообще.

* Упоминание регламента/закона/постановления хотя бы в одном текстовом поле: **466** из 732 (63.7%).
* Поле `legalActsFiles` заполнено у **34** услуг (4.6%).
* То есть у **266** услуг (36.3%) оператор не может сослаться на основание вообще.

**Предложение 4 (дополнение, приоритет №1).** Добавить в схему услуги отдельный структурированный блок:

```jsonc
"legalBasis": [
  {
    "type": "regulation",              // регламент | закон | постановление | приказ
    "title": "Административный регламент предоставления…",
    "actNumber": "№ 1234",
    "approvedBy": "Приказ МВД России",
    "date": "2024-03-15",
    "url": "http://publication.pravo.gov.ru/…",
    "validFrom": "2024-04-01",
    "validTo": null                     // для отслеживания устаревания
  }
]
```

Это даёт три вещи сразу: ассистент цитирует не «базу знаний», а конкретный пункт конкретного НПА; появляется машинная проверка устаревания (`validTo` в прошлом → карточку на ревизию); и становится возможной сверка со справочной правовой системой по номеру акта, а не по названию услуги.

### 6.2. Разрыв связи между файлами

В `flat_classification` у каждой категории есть массив `ids` — по замыслу это обратный индекс «ведомство → услуги». Фактически:

* в `ids` лежат UUID (`c3116b96-d854-…`);
* в `db_knowledge.id` лежат числа и строковые коды;
* **пересечение этих множеств — ноль элементов.**

Обратный индекс из справочника нерабочий. Связи в приложении восстановлены только по прямым полям услуги (`departmentId`, `mfcIds`, `lifeSituationIds`, `recipientIds`) — они как раз согласованы:

* `departmentId` не находится в справочнике у **2** значений, у **1** услуг ведомство не указано вовсе;
* `mfcIds` содержит **12** идентификаторов отделений, которых нет в справочнике `by_branch`.

**Предложение 5 (реструктуризация).** Привести идентификаторы к одному пространству имён (UUID) и оставить связь в одну сторону — от услуги к справочникам. Дублирующий массив `ids` в справочниках убрать: он весит 4 МБ из 4.4 МБ файла классификаторов и при этом не работает.

**Предложение 6 (реструктуризация).** Разделить сущности «услуга» и «вариант предоставления»:

```jsonc
{
  "id": "uuid-услуги",

```

## 8. Названия услуг

* Средняя длина названия — **166 символов**, максимум — **1000**.
* Длиннее 200 символов — **209** названий (28.6%).
* Короткого «человеческого» имени в схеме нет вообще.
* Нарушения единообразия: 1 назв. со строчной буквы, например «гсп на основании соцконтракта» — аббревиатура ГСП без расшифровки, в нижнем регистре, не по шаблону остальных.

Отдельная сложность: пары услуг различаются **только хвостом** названия — «…удостоверяющих личность гражданина Российской Федерации **на территории** Российской Федерации» и «…**за пределами территории** Российской Федерации». Обрезание слева делает их неразличимыми в списке.

**Предложение 7 (дополнение).** Добавить поля `shortTitle` (до 80 символов, для интерфейсов) и `aliases` (народные названия: «загранник», «прописка», «детские»). Сейчас короткое имя приложение строит эвристикой (`backend/app/ingest/build_index.py: short_title`), а синонимы ведёт в собственном словаре `data/dictionaries/synonyms.json` — это работа, которую логично делать один раз на стороне базы знаний.

## 10. Содержательные пробелы

Проверка типовыми запросами оператора показала, что часть базовых услуг в выгрузке отсутствует, хотя соответствующие жизненные ситуации заведены:

* **«свидетельство о рождении зарегистрировать ребенка»** — В выгрузке нет услуги «Государственная регистрация рождения», хотя есть жизненная ситуация «Рождение ребенка» (22 услуги).
* **«перемена имени поменять фамилию»** — Нет услуги «Государственная регистрация перемены имени», хотя есть одноимённая жизненная ситуация (12 услуг).
* **«архивная справка о стаже работы»** — Нет ни одной услуги по выдаче архивных справок.
* **«постановка в очередь в детский сад»** — Есть только внеочередное/первоочередное зачисление для льготных категорий; базовой услуги постановки на учёт в ДОУ нет.
* **«как записаться на прием в мфц»** — В базе знаний нет описания собственных сервисов МФЦ (запись на приём, выездное обслуживание, статус заявления) — оператор ищет их в других системах.

**Предложение 9 (дополнение).** Сверить каталог с перечнем услуг, фактически оказываемых в окне: расхождение «жизненная ситуация есть — услуги нет» должно быть блокирующей ошибкой выгрузки.
