# «Моисей»: обоснование решения

Ответ на пункты 1 и 2 технического задания: *как* оператор МФЦ получает быстрый
и достоверный ответ по приёму документов, и *почему* выбран именно такой способ.

---

## 1. Задача глазами оператора в окне

Условия, в которых работает специалист, задают все ограничения решения:

| Условие | Что из него следует |
|---|---|
| Более 700 услуг, 16 ведомств, экстерриториальный приём | Знать наизусть невозможно; нужен инструмент, а не обучение |
| Заявитель сидит напротив, очередь идёт | Ответ нужен за секунды, а не за минуты чтения регламента |
| Ошибка = повторный визит заявителя и жалоба | Правдоподобный, но выдуманный ответ хуже отсутствия ответа |
| Заявитель говорит «мне бы прописку сделать», а не называет услугу | Поиск обязан понимать разговорный язык |
| Часто нужна не одна услуга, а связка (родился ребёнок → 5 услуг) | Нужен подбор пакета, а не единичный результат |
| В окне бывает закрытый контур / нестабильный интернет | Система не должна умирать без внешнего API |

## 2. Рассмотренные варианты

| Вариант | Почему не подходит как основа |
|---|---|
| **Поиск по названию (как сейчас на сайте)** | Оператор должен заранее знать официальное название. «Загранник ребёнку» не найдёт «Оформление и выдача паспортов… за пределами территории Российской Федерации» |
| **Чат-бот на «голой» LLM** | Модель уверенно выдумывает размер пошлины и срок. Для окна приёма это неприемлемо: ответ выглядит достоверным и не проверяется |
| **Дообучение (fine-tuning) модели на базе знаний** | Регламенты меняются постоянно; каждое изменение = переобучение. Нет ссылки на первоисточник, нечего показать заявителю |
| **Только векторный поиск (эмбеддинги)** | Плохо работает на терминах и номерах («ЕГРН», «3-НДФЛ», «16-ЗТО»), требует внешнего сервиса эмбеддингов или тяжёлой модели в контуре |
| **Только полнотекстовый поиск (BM25)** | Не переживает опечатки и словоформы, не понимает «маткапитал» ≠ «материнский капитал» |

## 3. Выбранное решение

**RAG (Retrieval-Augmented Generation) поверх очищенной базы знаний с обязательным
цитированием источника и работоспособностью без LLM.**

```
запрос оператора
   │
   ├─ 1. Понимание запроса ─── раскладка ЙЦУКЕН/QWERTY, морфология (pymorphy3),
   │                           словарь сокращений (73 статьи, 241 форма), опечатки
   │
   ├─ 2. Гибридный поиск ───── BM25 по леммам  ─┐
   │                           символьные 3-4-граммы ─┼─ RRF ─→ фрагменты
   │                           BM25 по названиям услуг ┘
   │
   ├─ 3. Кэш (услуга + вопрос) ─── попадание → ответ за миллисекунды
   │
   ├─ 4. Генерация ─────────── Claude отвечает ТОЛЬКО по переданным фрагментам,
   │                           каждое утверждение со ссылкой [n]
   │                           ↓ нет ключа / нет сети
   │                           автономный режим: выдержки из базы без генерации
   │
   └─ 5. Ответ ─────────────── текст + список источников: услуга → раздел →
                               оригинальный текст из db_knowledge.json
```

### Почему именно RAG

1. **Достоверность проверяема.** Модель физически не видит ничего, кроме
   выданных ей фрагментов базы знаний. В промпте прямо запрещено дополнять ответ
   общими знаниями, а каждое утверждение обязано нести ссылку `[n]`. Оператор
   одним кликом раскрывает источник: название услуги, раздел карточки и
   исходный текст поля — вплоть до сырого HTML из выгрузки.
2. **Обновление данных без переобучения.** Новая выгрузка с mfc71.ru →
   `python -m app.ingest.build_index` (5 секунд) → система знает новое.
   Индекс пересобирается автоматически при изменении исходных файлов.
3. **Отсутствие ответа — тоже ответ.** Если в базе нет сведений, Моисей обязан
   сказать «в базе знаний нет ответа» и подсказать, где уточнить. Это лучше,
   чем правдоподобная выдумка, и это то, чего не даёт «голая» LLM.

### Почему гибридный поиск, а не эмбеддинги

Три канала дополняют друг друга и закрывают разные типы промахов:

| Канал | Что ловит | Пример |
|---|---|---|
| BM25 по леммам | точные термины регламента | «госпошлина», «ЕГРН», «16-ЗТО» |
| Символьные n-граммы | опечатки, словоформы, обрывки | «паспрт», «заграничнй», «прописатся» |
| BM25 по названиям услуг | когда оператор называет услугу почти дословно | «признание гражданина банкротом» |

Ранги объединяются через **RRF** (Reciprocal Rank Fusion) — это избавляет от
калибровки несопоставимых шкал между каналами.

Практический аргумент: всё считается локально, без внешнего сервиса эмбеддингов
и без тяжёлой нейросети в контуре. Индекс — 68 МБ, собирается за 5 секунд,
работает на обычном рабочем месте. Для МФЦ с ограниченным доступом в интернет
это не оптимизация, а условие внедряемости.

### Измеренное качество поиска

На наборе из 39 реальных формулировок оператора
(`backend/tests/eval_queries.json`, запуск `python -m tests.eval_search`):

| Метрика | Значение |
|---|---|
| Recall@1 | 71.8% |
| Recall@3 | 87.2% |
| Recall@5 | **97.4%** |
| Recall@10 | 100% |
| MRR | 0.812 |
| Латентность (медиана / p95) | **13 мс / 29 мс** |

Набор включает намеренно «грязные» запросы: `ghjgbcrf` (латинская раскладка),
`скок стоит выписка егрн`, `банкротство физлица через мфц`, `маткапитал`.

### Почему система обязана работать без LLM

Автономный (extractive) режим — не заглушка, а полноценный рабочий сценарий.
Без ключа API Моисей не генерирует текст, а собирает ответ выдержками из
найденных фрагментов с указанием услуги и раздела. Оператор всё равно получает
нужный кусок регламента за секунду вместо пролистывания карточки. Это даёт:

* внедряемость в закрытом контуре, где внешние API запрещены;
* отказоустойчивость — при недоступности API окно приёма не встаёт
  (ответ деградирует, а не исчезает);
* демонстрируемость — приложение запускается «из коробки», без ключей.

## 4. Ключевые продуктовые решения

### 4.1. Мастер по жизненной ситуации

Заявитель не говорит «мне нужна услуга №7100000000181110272». Он говорит
«у меня родился ребёнок». Мастер ведёт оператора по короткому опросу
(«что уже оформлено» → «какие выплаты нужны» → «особые обстоятельства») и
выдаёт **пакет связанных услуг**: порядок обращения по этапам, срок и стоимость
каждой услуги и — главное — **сведённый чек-лист документов на весь пакет**.

Оператор видит: «паспорт нужен в 8 из 9 услуг пакета» — и просит документ
один раз, а не девять. Сведение работает через онтологию типовых документов
(`data/dictionaries/document_types.json`), потому что в регламентах один и тот же
паспорт описан десятком формулировок.

Сценарии не привязаны к идентификаторам услуг: каждый вариант ответа задаёт
поисковые запросы, которые резолвятся через тот же гибридный поиск. Поэтому
обновление выгрузки не ломает мастер.

### 4.2. Кэш ответов по паре (услуга, вопрос)

Вопросы в окне повторяются: «какие документы на загранпаспорт» спрашивают
десятки раз в день во всех отделениях. Каждый такой вопрос — 6–10 тыс. входных
токенов контекста.

Ключ кэша строится не по сырой строке, а по **нормализованному представлению
вопроса**: леммы без служебных слов, упорядоченные. Поэтому
«какие документы нужны на загранпаспорт», «Документы на загранпаспорт?» и
«загранпаспорт: какие документы» — одно попадание. При этом «сколько стоит
загранпаспорт» и «срок изготовления загранпаспорта» дают разные ключи:
слова, различающие намерение, из ключа не выбрасываются.

В ключ входят модель и версия промпта — после их смены кэш инвалидируется сам.
Экономия (токены, деньги, время) считается и показывается на вкладке
«Данные и кэш».

### 4.3. Группировка муниципальных дублей

59% каталога (432 из 732 услуг) — это 24 муниципальные услуги, продублированные
по 26 муниципальным образованиям. Без группировки поиск «градостроительный план»
выдаёт 26 одинаковых строк. Система определяет такие группы автоматически и
показывает одну услугу с выбором муниципалитета.

### 4.4. Чек-лист приёма вместо «простыни»

Перечень документов — не текст, а интерактивный чек-лист с отметками,
счётчиком и копированием в буфер. Прогресс сохраняется по услуге: оператор
отмечает принятое прямо во время приёма.

### 4.5. Честность о качестве данных

Приложение не делает вид, что база полна. Услуги с неполной карточкой помечены
и понижены в выдаче, в карточке видно, каких разделов нет, а вкладка «Данные и
кэш» показывает полную картину качества выгрузки. Оператор должен знать, когда
сведения нужно перепроверить в справочной правовой системе.

## 5. Преимущества решения — сводно

| Преимущество | Как обеспечено |
|---|---|
| **Достоверность** | Ответ только по фрагментам базы; обязательные ссылки `[n]`; показ оригинального текста поля; явное «в базе нет ответа» |
| **Скорость** | Поиск 13 мс (медиана); кэш отдаёт повторный ответ мгновенно; ответ ассистента стримится по мере генерации |
| **Понимание оператора** | Раскладка, морфология, 73 статьи словаря сокращений, исправление опечаток; интерфейс показывает, *как* понят запрос |
| **Актуальность** | Обновление = замена JSON и пересборка индекса за 5 секунд, без переобучения |
| **Работа в закрытом контуре** | Поиск полностью локальный; автономный режим ответов без внешнего API |
| **Экономия** | Кэш по паре (услуга, вопрос) с подсчётом сэкономленных токенов и денег |
| **Пакетное обслуживание** | Мастер по жизненной ситуации: связка услуг и единый чек-лист документов |
| **Управляемость** | Отчёт о качестве данных прямо в интерфейсе — видно, что дозаполнять |

## 6. Ограничения и что дальше

Честный список того, что решение **не** делает:

* **Не заменяет справочную правовую систему.** Моисей отвечает по базе знаний
  МФЦ. Для сверки с действующей редакцией НПА нужна СПС — и именно поэтому
  предложение №4 в [анализе данных](DATA_ANALYSIS.md) о структурированном блоке
  `legalBasis` является приоритетным: без реквизитов акта автоматическая сверка
  невозможна.
* **Качество ответа ограничено качеством выгрузки.** У 41% услуг в тексте нет
  ни одной ссылки на нормативный акт; у 45 услуг карточка заполнена менее чем
  наполовину. Обработкой это не лечится.
* **Оценка поиска — на 39 запросах.** Набор составлен по типовым обращениям, но
  для промышленной эксплуатации его нужно расширять на реальных логах окна.

Направления развития: обратная связь оператора («ответ помог / неверен») как
источник для доработки базы; журнал вопросов без ответа как список пробелов
в базе знаний; подключение СПС по реквизитам НПА; распознавание вопросов
голосом в окне.
